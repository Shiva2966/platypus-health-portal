# Database design, reliability and operations

Health Portal runs as **one central server with one database**. Production = **PostgreSQL 16**;
local dev/tests = **SQLite** (WAL). Everything below is verified by `tests/test_db_*.py` on both engines.
*(Demo with synthetic data. Not HIPAA-compliant - see `DEPLOY.md`.)*

## 1. Configuration (`app/db.py`)

| Variable | Default | Meaning |
|---|---|---|
| `DATABASE_URL` | `sqlite:///data/app.db` | `postgresql+psycopg://user:pw@host:5432/db` in production. `postgres://` / `postgresql://` are rewritten to the psycopg3 driver. |
| `HP_TEST_DATABASE_URL`, `HP_DB_PATH` | unset | Test isolation. **They win over `DATABASE_URL`**, so a test run can never touch the real database. |
| `AUTO_MIGRATE` | `0` | `1` = `alembic upgrade head` at startup (production). `0` = `create_all` (dev). |
| `DB_POOL_SIZE` / `DB_MAX_OVERFLOW` / `DB_POOL_TIMEOUT` / `DB_POOL_RECYCLE` | 10 / 20 / 30 s / 1800 s | PostgreSQL pool. `pool_pre_ping` is always on. |
| `DB_STATEMENT_TIMEOUT_MS` / `DB_LOCK_TIMEOUT_MS` / `DB_IDLE_TX_TIMEOUT_MS` | 30000 / 10000 / 60000 | Server-side timeouts set per connection (a stuck query or forgotten transaction cannot hold the system hostage). |
| `SQLITE_BUSY_TIMEOUT_MS` | 30000 | SQLite lock wait. |

**SQLite** (connect event, the only place with engine-specific SQL): `foreign_keys=ON`, `journal_mode=WAL`,
`synchronous=NORMAL`, `busy_timeout`. **PostgreSQL**: psycopg3, pooled, timeouts above, `application_name`.

Sessions: one per request (`get_db`). Routes call `db.commit()`; anything left uncommitted - or an
exception - is rolled back (an uncommitted ORM change logs a PHI-free warning). Scripts use `session_scope()`.
Multi-step writes (record + audit + notification) are one transaction: they commit or roll back together
(`test_db_transactions_audit.py`).

## 2. Schema rules, enforced centrally (`app/db_ops/policies.py`)

Applied in `import_all_models()` and before every `create_all`, and used by Alembic autogenerate, so they hold
for every model module regardless of author:

* **Timestamps** - every `DateTime` becomes `UTCDateTime`: `timestamptz` on PostgreSQL; Python values are
  *naive UTC* on both engines (matches the app's `utcnow()` helpers; no naive/aware comparison errors).
* **Foreign keys** - added where models only declared a bare id string, always with explicit `ondelete`
  (nullable -> `SET NULL`, required -> `RESTRICT`, ownership -> `CASCADE`). Policy-added FKs are
  `DEFERRABLE INITIALLY DEFERRED` (checked at COMMIT) so unit-of-work flush order never matters.
* **Indexes** - every FK column, plus searched columns (names, dates, status, recipient/unread, audit by patient/time).
* **CHECK constraints** for status/enum/size columns (see `CHECKS`); models may add their own (same name wins).
* **Uniqueness** - `lower(email)` for patients and staff; one *live* document per `(patient_id, sha256)`
  (partial unique index `WHERE deleted_at IS NULL`).
* No `Float` money (tests fail on it), ids are `String(36)` UUIDs, files are `LargeBinary`.

`tests/test_db_constraints.py` checks these rules against the real metadata and proves FK/UNIQUE/CHECK/CASCADE
behaviour on live databases.

### Soft-delete convention
`deleted_at TIMESTAMP NULL` (documents). Queries must add `deleted_at IS NULL`; uniqueness is expressed with
partial indexes on that predicate so a deleted row never blocks re-creation. Hard purge is a deliberate
retention job (not implemented). `audit_log` is never deleted.

## 3. Append-only audit log
`audit_log` has **no foreign keys** (history outlives accounts) and **triggers that reject every UPDATE and
DELETE** (and TRUNCATE on PostgreSQL), on both engines. Installed by `ensure_db_objects()` at startup and by
migration `0002`; `/readyz` goes red if they are missing. Even a SQL-injection or a buggy admin screen cannot
rewrite history. Only a database owner who drops the trigger can (that itself should be monitored).

## 4. Migrations (Alembic)
* `alembic/env.py` imports **all** `app.models.*`, applies the policies, uses `DATABASE_URL`, SQLite batch mode,
  PostgreSQL advisory lock so concurrent replicas migrate one at a time.
* Revision `0001` = autogenerated schema; `0002` = triggers, functional indexes, PostgreSQL blob storage tuning.
* Workflow: change a model -> `.\scripts\migrate.ps1 new "what changed"` -> review -> commit. Apply with
  `.\scripts\migrate.ps1` (or `AUTO_MIGRATE=1`). `.\scripts\migrate.ps1 check` and
  `test_models_and_migrations_have_not_drifted` fail if models and migrations disagree.
* Pre-release only: `python scripts/regen_initial.py` rebuilds `0001`. Once any real database exists, never again.
* A dev database created by `create_all` has no `alembic_version`; `AUTO_MIGRATE=1` refuses to guess and tells
  you to verify and `alembic stamp head` (or restore a backup into an empty DB).

## 5. Large files (BLOBs)
Files live in `document_blobs(document_id PK/FK -> documents ON DELETE CASCADE, data)`; `documents` is metadata
only, so list/search never touches bytes (a test asserts the model has no data column). PostgreSQL column uses
`STORAGE EXTERNAL` (no pointless compression of PDFs/JPEGs; enables cheap sliced reads).
`app.db_ops.integrity.iter_blob_chunks()` streams a file in 1 MiB `substr()` slices.

Measured on this Windows laptop (Python 3.12, PostgreSQL 16.2 embedded, SQLite 3, random 15 MB payloads;
`python scripts/bench_blobs.py --url <scratch db>`):

| | SQLite | PostgreSQL |
|---|---|---|
| upload 15 MB, sequential (median) | 189 ms | 687 ms |
| 4 concurrent 15 MB uploads (total) | 644 ms | 1995 ms |
| list 8 docs / 120 MB of blobs (metadata query) | 0.15 ms | 0.54 ms |
| read 15 MB in one query | 54 ms | 735 ms |
| stream 15 MB in 1 MiB slices | 622 ms (SQLite re-reads per slice; code reads once) | 252 ms |
| sha256-verify 126 MB | 4.7 s | 2.0 s |

Conclusion: fine for the 15 MB limit. The list path is independent of blob volume. Weak spot: a single
`SELECT data` of 15 MB on PostgreSQL is ~3x slower than slicing (driver text/bytea decoding) - W2's download
endpoint currently loads the whole blob into memory; switching it to `iter_blob_chunks` + `StreamingResponse`
would cut latency and memory per download.

## 6. Integrity tools
* `python scripts/verify_blobs.py` - recomputes sha256 + size of every file, finds missing/orphan blobs and
  orphan rows for **every** FK (plus polymorphic notification recipients). Read-only; exit 1 on any problem.
* `/healthz` - process up. `/readyz` - DB reachable, migration state (must be at head when `AUTO_MIGRATE=1`),
  audit triggers present. 503 otherwise. No PHI in either.

## 7. Backup and restore
```
.\scripts\backup.ps1 -Keep 14 -VerifyRestore     # or: python scripts/backup.py --verify-restore
.\scripts\restore.ps1 -Latest -Target sqlite:///data/restored.db
.\scripts\restore.ps1 -Backup backups\healthportal_...pgdump -Target postgresql+psycopg://hp:pw@host/db_new
```
* SQLite: online `sqlite3` backup API (consistent while the app runs), stored as one file.
* PostgreSQL: `pg_dump -Fc` at an **exported snapshot**, so the manifest's row counts and blob digest describe
  exactly what is in the dump.
* Each backup has `<file>.manifest.json`: table row counts, alembic revision, blob count/bytes/digest, sha256 of
  the dump file. Contains no patient data.
* `restore` refuses a non-empty target without `--force`, verifies the dump checksum, restores, then checks row
  counts, every blob sha256, orphans, `integrity_check` (SQLite) and migration revision.
  `--verify-restore` does a full restore into a scratch database after every backup.
* Retention: newest `BACKUP_KEEP` (default 14) kept; the newest is never pruned.
* Cross-engine restore (SQLite dump into PostgreSQL) is deliberately unsupported.

### RPO / RTO - honest numbers
* **RPO (data you can lose)**: with nightly dumps = **up to 24 h**. Hourly cron = 1 h. Real point-in-time
  recovery (RPO of seconds) needs WAL archiving: managed PostgreSQL with PITR (Render/Neon/Supabase/RDS paid
  tiers) or pgBackRest/WAL-G on a VPS. **Not configured here.**
* **RTO (time to be back)**: measured restore+verify of a 126 MB blob-heavy database on a laptop: 38 s on
  PostgreSQL (backup + restore + 2 hash passes), 4 s on SQLite. Incompressible files restore at a few MB/s
  with `pg_restore`; budget roughly 10 min per GB plus 10-30 min to provision a replacement server and point DNS.
  Realistic RTO for this demo: **under an hour if backups are somewhere else**. Backups stored only on the
  same disk/VPS are not a disaster-recovery plan: copy them off-site (`rclone`, object storage) - not automated here.
* The restore path is **tested** (`tests/test_db_backup_restore.py`, CLI end-to-end) - run `-VerifyRestore`
  regularly and do a real restore drill before relying on it.

## 8. Testing on both engines
```
.\scripts\test_all.ps1                 # full suite on SQLite, then on embedded PostgreSQL 16 (pip pgserver)
.\scripts\test_all.ps1 -Engine postgres -Pytest "-q tests/test_db_*.py"
$env:HP_TEST_DATABASE_URL="postgresql+psycopg://hp:pw@localhost:5432/scratch"; pytest   # any PostgreSQL
```
`pgserver` (`pip install -r requirements-pgtest.txt`) is dev-only and needs no Docker or installer.
Each `test_db_*` test gets its own scratch database (SQLite file or `CREATE DATABASE`), dropped afterwards.

## 9. Known limits / risks
* SQLite is for dev only: one writer at a time; a read-then-write transaction can still hit `database is locked`
  under heavy concurrency (busy timeout 30 s mitigates).
* Several uvicorn workers/replicas: schema work is serialised by an advisory lock; W2's background sweep thread
  runs per process (idempotent, but doubled). Default is one worker.
* No replication / automatic failover / PITR out of the box (single PostgreSQL container). A managed database
  gives these.
* Encryption at rest is **not** provided by the app or compose file (use disk/volume or managed-DB encryption).
* Policy-added foreign keys are deferred, so violations surface at COMMIT instead of at the offending statement.
* `Documents` hold PHI-like content in the database in clear form; backups contain it too - protect them.
